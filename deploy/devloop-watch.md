# Сторож группы dev-loop (`ops-mcp watch`)

Сторож следит за Telegram-группой «AI Bridge Dovira» (`-1003928414397`). Когда там пишет человек, он запускает облачную
рутину Claude Code «Dovira Task Coordinator» и передаёт ей id новых сообщений:

```
DEVLOOP-WAKE chat=-1003928414397 ids=672,673,675 (last=675)
```

Дальше всё делает координатор: читает историю группы, сверяет её с реестром в Notion, заводит сессии задач или
доставляет сообщение в уже работающую сессию.

Чего сторож не делает:

- не принимает решений по содержимому сообщений;
- не пишет в группу: ни ответов, ни реакций, ни отметок о прочтении;
- не трогает пользовательскую сессию Давида (сервер `telegram`).

Он слушает Bot API `getUpdates` бота devloop. Сообщения он дополнительно записывает в инбокс, его читает инструмент
`devloop_inbox` сервера ops-mcp.

## Где живёт

Сервис `devloop-watcher` в `deploy/megamcp-stack.yml`: тот же образ `metamcp-all-in-one`, команда
`/usr/local/bin/ops-mcp watch`, `restart: always`, том `ops_mcp_data` (`/var/lib/ops-mcp`). Этот же том смонтирован и в
контейнер MetaMCP. Через него работают:

- `/var/lib/ops-mcp/devloop/state.json` — offset `getUpdates`, до какого события уже был запуск, время последних
  запусков и алерта;
- `/var/lib/ops-mcp/devloop/inbox.jsonl` — записанные сообщения и нажатия;
- `/var/lib/ops-mcp/devloop/callbacks.jsonl` — очередь нажатий для `telegram-devloop-bot`.

Пути отличаются от тех, что были в задаче (`/opt/telegram/data/...`). Сторож работает в отдельном контейнере, и общий
с MetaMCP у него только этот том.

## Поведение

- **Фильтр.** Будят рутину только сообщения и правки людей из `WATCH_CHAT_ID`. Пропускаются:
  - сообщения ботов (`from.is_bot`);
  - сообщения без отправителя;
  - служебные события (вход, закреп, смена названия и т. п.);
  - другие чаты.
- **Нажатия inline-кнопок.** У бота один потребитель `getUpdates` — сторож. Каждое нажатие он дописывает в очередь
  (Bot API update + `"answered": true`) и сам вызывает `answerCallbackQuery`. `telegram-devloop-bot` →
  `message(action="callbacks")` читает их из очереди. Рутину нажатия не будят.
- **Дебаунс и лимит.** После первого нового сообщения сторож ждёт 20 с (`WATCH_DEBOUNCE_SECONDS`) и отправляет всё
  накопленное одним запуском. Между запусками — минимум 120 с (`WATCH_MIN_INTERVAL_SECONDS`), плюс страховочный потолок
  30 запусков в час. Пришедшее в паузе уходит следующим запуском, ничего не теряется.
- **Ответы fire API:**

  | Ответ | Что делает сторож |
  |:--|:--|
  | 200 | Запуск засчитан, в лог идёт `session=…`. Не повторяется никогда. |
  | ответа не было | Повтор с backoff. |
  | 429 | Ждёт `Retry-After` и повторяет. |
  | 5xx | Backoff 15 с → 5 мин. |
  | 400/401/403/404 | Строка `ERROR CONFIG` в лог, повторов нет до рестарта. |

  В случае 4xx id остаются в состоянии и уходят после рестарта с исправленным env.
- **Рестарт.** Offset и инбокс пишутся одним шагом под блокировкой. Отметка о запуске пишется сразу после 200. Поэтому
  рестарт не дублирует запуск и не теряет сообщения; не защищён только крах ровно между ответом 200 и записью.
- **Здоровье:**
  - в stdout пишется строка на каждый запуск (`devloop watcher: fired "…" session=…`) и на каждую ошибку
    (`ERROR …`);
  - алерт Давиду в личку `375465077` через бота `telegram-bot-go` уходит, если 3 запуска подряд неудачны, рутина
    отклонила запуск как ошибку конфигурации или нет связи с Telegram больше 10 минут;
  - алерт приходит не чаще раза в час;
  - в группу сторож не пишет никогда.
- **Аренда (`devloop_lease`)** больше не придерживает запуски: каждое новое сообщение идёт координатору, он сам решает,
  куда его доставить.

## Переменные

Задаются в env стека `megamcp` в Portainer (Stacks → megamcp → Environment variables), не в git.

| Переменная | Значение | Секрет |
|:--|:--|:--|
| `WATCH_BOT_TOKEN` | токен бота devloop (тот же, что у `telegram-devloop-bot`); старое имя `DEVLOOP_BOT_TOKEN` тоже подхватывается | да |
| `ROUTINE_TOKEN` | `sk-ant-oat01-…`, API-триггер рутины; старое имя `DEVLOOP_ROUTINE_TOKEN` тоже подхватывается | да |
| `WATCH_ALERT_BOT_TOKEN` | токен бота `telegram-bot-go` для алертов | да |
| `ROUTINE_ID` | `trig_01M9keX9E8Xn64kVb4uCqC58` (по умолчанию) | |
| `WATCH_CHAT_ID` | `-1003928414397` (по умолчанию) | |
| `WATCH_ALERT_CHAT_ID` | `375465077` (по умолчанию) | |
| `WATCH_DEBOUNCE_SECONDS` / `WATCH_MIN_INTERVAL_SECONDS` | 20 / 120 | |
| `DEVLOOP_ENABLED` | `true` по умолчанию; `false` выключает сторожа | |

Без `WATCH_BOT_TOKEN`, `WATCH_CHAT_ID`, `ROUTINE_ID` или `ROUTINE_TOKEN` сторож пишет одну строку
`not started: missing required environment: …` и простаивает, а не падает в цикл перезапусков. Остальные сервисы стека
от него не зависят.

Токены в лог и в `state.json` не попадают: из текста ошибок они вырезаются.

## Что Давид делает руками

1. **BotFather** → `/setprivacy` → бот devloop → **Disable**. Затем удалить бота из группы и добавить заново: privacy
   применяется при входе. Лучше сделать его админом группы.
2. Убедиться, что у бота нет вебхука и другого читателя `getUpdates`. Иначе сторож пишет в лог 409 Conflict.
3. Вписать в env стека `ROUTINE_TOKEN`, `WATCH_BOT_TOKEN` и `WATCH_ALERT_BOT_TOKEN`. Если в стеке явно стоит
   `DEVLOOP_ENABLED=false`, убрать его или поставить `true`.
4. Проверить, что у сервера `telegram-devloop-bot` в MetaMCP есть env
   `TELEGRAM_CALLBACK_QUEUE_FILE=/var/lib/ops-mcp/devloop/callbacks.jsonl`.
5. Обновить стек (Update the stack с re-pull), чтобы контейнер `megamcp-devloop-watcher` пересоздался на новом образе.

## Проверка на стенде

Смотреть лог: `docker logs -f megamcp-devloop-watcher`.

- При старте в логе `devloop watcher: started chats=[-1003928414397] routine=trig_01M9… …`.
- Человек пишет в группу. Не позже чем через ~2,5 минуты в логе появляется
  `fired "DEVLOOP-WAKE chat=… ids=<id> (last=<id>)" session=https://claude.ai/code/…`.
- Три сообщения подряд уходят одним `fired` с тремя id.
- Сообщение бота запуска не вызывает.
- После рестарта контейнера нет повторного `fired` с теми же id.
- Нажатие кнопки бота devloop видно через `telegram-devloop-bot` → `message(action="callbacks")`.
